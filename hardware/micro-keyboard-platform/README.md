## Overview

The **Micro Keyboard Platform (MKP)** is a compact and modular physical
keyboard platform designed for embedded systems.

MKP is not simply a keyboard matrix.

It is an active input device with its own microcontroller, responsible for
scanning the keyboard, processing key events, implementing layers and
communicating with the host system.

The central design principle is:

> **The MKP is a keyboard, not a keyboard matrix.**

The host does not need to know how the keyboard matrix works. It only needs
to consume the events generated by the MKP.

The current hardware revision is based on the **RP2040-Zero** and provides:

- 50 physical keys;
- 5 × 10 keyboard matrix;
- per-key diodes;
- native USB HID capability;
- UART host interface;
- I2C host interface;
- SPI host interface;
- programmable WS2812B RGB status indicator;
- dedicated external 5 V power input.

## Why MKP?

MKP originally started as a compact keyboard for a specific embedded
terminal.

During development, the project evolved beyond that original requirement.

Instead of creating a keyboard tied to one device, the architecture was
redesigned as an independent platform capable of being reused by different
hosts.

This allows the same keyboard hardware to be integrated into:

- microcontroller projects;
- Linux SBCs;
- portable terminals;
- cyberdecks;
- communication devices;
- instrumentation;
- experimental embedded systems;
- conventional computers through USB HID.

The hardware provides capabilities.

The firmware defines behavior.

          50 keys      UART/I2C/SPI     GP29

The keyboard matrix belongs entirely to the MKP.

## Keyboard

The Revision B keyboard uses a **5 × 10 electrical matrix** with
**50 physical switches**.

~~~text
┌────┬────┬────┬────┬────┬────┬────┬────┬────┬────┐
│ 1  │ 2  │ 3  │ 4  │ 5  │ 6  │ 7  │ 8  │ 9  │ 0  │
├────┼────┼────┼────┼────┼────┼────┼────┼────┼────┤
│ Q  │ W  │ E  │ R  │ T  │ Y  │ U  │ I  │ O  │ P  │
├────┼────┼────┼────┼────┼────┼────┼────┼────┼────┤
│ A  │ S  │ D  │ F  │ G  │ H  │ J  │ K  │ L  │ENT │
├────┼────┼────┼────┼────┼────┼────┼────┼────┼────┤
│ FN │CAPS│ Z  │ X  │ C  │ V  │ B  │ N  │ M  │CTRL│
└────┴────┴────┴────┴────┴────┴────┴────┴────┴────┘
~~~

The remaining switches provide:

~~~text
A / B / X / Y

UP / DOWN / LEFT / RIGHT

SPACE

SW49 — firmware-defined function
~~~

The exact function of special keys remains configurable by firmware.

## Host Interfaces

The MKP can communicate with a host through two fundamentally different
interfaces.

### USB

The native USB interface of the RP2040 allows the MKP to operate directly
as a USB HID keyboard.

### Embedded Host Interface

A dedicated connector exposes four configurable signals:

~~~text
HOST_SIG1
HOST_SIG2
HOST_SIG3
HOST_SIG4
GND
~~~

These signals support:

~~~text
UART
I2C
SPI
~~~

Protocol selection is handled entirely by firmware.

Revision B does **not** use hardware protocol-selection jumpers, ADC
identification or resistor networks.

---

## RGB Status Indicator

Revision B includes one **WS2812B-5050** addressable RGB LED connected to
GP29.

Its behavior is firmware-defined and may represent:

- initialization;
- active layer;
- communication mode;
- Caps Lock;
- activity;
- error conditions;
- application-specific status.

---

## Mechanical Philosophy

MKP follows a **mechanical-first** design approach.

Keyboard geometry is primarily determined by:

- ergonomics;
- key spacing;
- physical dimensions;
- enclosure constraints;
- future faceplate integration.

Electrical routing adapts to the keyboard geometry rather than defining it.

Revision B places:

~~~text
TOP
├── switches
└── WS2812B

BOTTOM
├── RP2040-Zero
├── matrix diodes
├── passive components
├── host connector
└── power connector
~~~

The earlier experimental dual-side footprints were intentionally removed
from Revision B.

## Design Principles

The Revision B architecture reflects a few core engineering principles:

- The MKP is a keyboard, not a keyboard matrix.
- The host consumes events instead of controlling the matrix.
- Hardware provides capabilities; firmware defines behavior.
- Mechanical requirements come before routing convenience.
- Useful flexibility should be preserved.
- Complexity without practical benefit should be removed.
- Engineering decisions and their history should be documented.
- The platform must remain independent from any single host.
